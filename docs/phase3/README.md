Phase 3 implements the versioned agent control plane. The Master implementation prompt controls scope; source files and executed tests establish current behavior. Historical phase reports are checkpoints, not implementation evidence.

The existing `/api/v1/agents` namespace is extended instead of creating a parallel `/ai-agents` API. `/ai-studio` lists assistants and creates an inactive draft. `/ai-studio/[id]` edits identity, instructions, languages, approved provider policy, knowledge references and the compatibility flow reference. Owners and administrators can save, run deterministic configuration checks, review the diff, publish, restore a historical configuration and assign WhatsApp devices. Other active members can review.

Publication requires `expectedRevision` and `expectedPublishedVersionId`. A draft save increments its revision and invalidates its test receipt. The database locks the stable agent row, checks membership and references, creates an immutable snapshot and normalized links, updates the published pointer and appends an audit event in one transaction. Stale edits and publications return 409. Restoring a historical version creates a new version and replaces the saved draft; it does not mutate history.

The draft test endpoint performs deterministic configuration and instruction checks. It does not claim to evaluate provider response quality, generate a real model response, execute arbitrary tools or send WhatsApp messages. The effective instruction preview and release diff are available before publication. Full playground and additional policy editors belong to later phases.

`modules/config/RuntimeConfigResolver.ts` reads the authoritative pointer on each reply. WhatsApp passes its device ID, which must resolve through a tenant-owned channel link. The upgrade automatically links a device only when its organization has exactly one active agent. Missing assignments or ambiguous agent selection produce an explicit configuration conflict. Company and property handlers retain their existing deterministic framework behavior. General model replies use published identity, instructions, language and model bounds. Only published knowledge IDs can be retrieved. Browser chat delegates to the backend.

Legacy agent columns are preserved during backfill and remain readable for compatibility. Editing those compatibility fields does not publish runtime instructions. New agents require their first explicit publication. Historical agent deletion and deletion of a knowledge base referenced by published history return a conflict. A deleted compatibility flow reference must be removed from the draft and republished before that configuration can resolve again.

Migrations `019_agent_versions.sql` and `020_agent_runtime_links.sql` are additive. They have been prepared for local replay only. No live project has been changed. Direct authenticated REST writes to `agents` and access to the new control tables/RPC are denied; the backend authorizes stored membership. The new functions use invoker privileges with PUBLIC/anon/authenticated execution revoked.

To verify locally, run `node scripts/phase3-verify.mjs`. It collects every required gate in `verification.json`, including inherited failures. `npm run test:agents:db` uses the pinned Supabase `self-hosted/v0.8.2` Docker distribution with generated credentials, isolated project names, loopback ports and temporary storage. It refuses live environment files, replays all active SQL in deterministic filename order including both 011 files, excludes `legacy/`, fails on SQL replay errors and removes its own stack. Provider and WhatsApp seams are stubbed; external test requests are blocked. Generated credentials stay in ignored local test results and are not copied into phase evidence.
